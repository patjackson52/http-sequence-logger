Network Log Lab — component & style specification

Companion to the prototype (Network Log Lab.dc.html) and the mockup sheet (Mockups.dc.html). §1–6 describe what the prototype builds today. §7–15 (this revision) extend the design to SDK → app handler invocations and the return of control, following log-model draft 1.1. They are design specification only: the web viewer has not been updated to render them, and the native logger is not claimed to capture anything beyond the model in §7.

Source of truth. §7–15 follow patjackson52/http-sequence-logger: HANDLER-TRACING.md, CONTRACT.md (format 1.1 draft), examples/handler-*.ndjson, samples/live/successful-sign-in.ndjson and DemoAuthSdk.kt. Fixture files are copied into this project unchanged. Where the repository names differ from the prototype's synthetic v: 1 vocabulary, the repository wins.

5 · Architecture (prototype)

nll-data.jsSynthetic NDJSON fixtures (generated line by line), parseNdjson() → events + diagnostics, reconstruct() → sessions / recordings / operations / exchanges. Pure; never evaluates content or touches the network. Its fixtures use the prototype's own v: 1 vocabulary (operation.start / parentOpId), not draft 1.1; the mapping is given in §7. nll-layout.jslayoutSequence(session, {hidden, collapsed, laneWidth, recordingId}) → lanes, rows, arrows, bars. Deterministic; independent of parsing. §9 adds localArrows and waitSegments to the output shape (proposed). Network Log Lab.dc.htmlReact state + view-model; composes NLL Sequence (SVG shapes + HTML labels) and NLL Inspector. TypesThe prototype runs as plain JavaScript so it opens with no build step; the TypeScript shapes it follows are declared as tsType annotations on the component props (SequenceLayoutView, InspectorViewModel, InspectorTab). Porting to .tsx is mechanical.

Revision — handler invocations

Scenario: the app passes a handler to DemoAuthSdk.authenticate(handler). While authenticate runs it invokes CustomerTaskHandler.loadTask() synchronously; the handler may call GET https://jsonplaceholder.typicode.com/todos/1 with the customer's own HTTP client, then returns; DemoAuthSdk.acceptTask runs; authenticate ends. Ownership changes and method boundaries must be visible with zero HTTP. Servers (dummyjson.com, httpbin.org, jsonplaceholder.typicode.com) are public demo services.

7 · Information model — draft 1.1 handler spans

Envelopeschema_version="1.1" · event_type · event_id · session_namespace · session_id · recording_id · sequence · timestamp · monotonic_ns (decimal string) · data · context{trace_id, span_id, parent_span_id, parent_scope} on span events · optional extensions VocabularySession grouping key is (session_namespace, session_id); each recording keeps its own sequence and monotonic clock. HTTP events are http.request.started · http.response.headers · http.body.captured · http.trailers · http.ended · http.metrics; HTTP outcomes are success · http_error · transport_error · timeout · cancelled · unknown (the prototype's “transport_failure” maps to transport_error). Owners are integrator · sdk · system · unknown; the “App code” lane is owner=integrator. Handler startevent_type="operation.started", data: name, origin{owner, component, method} (the callee), invocation{kind:"handler", dispatch:"synchronous", caller{owner, component, method}}. caller is the immediate caller, not the business initiator. Each invocation has its own span_id; parent_span_id is the calling SDK operation when it was instrumented. Handler endevent_type="operation.ended" with the same context.span_id; data: outcome · completion · duration_ns · error (sanitized; stage="unknown" does not make it a network error). Pairing is by span identity only — never by order, name or timestamp. Child HTTPA request whose context.parent_span_id equals the handler span_id is causally nested under it. HTTP origin keeps its own initiator and executor actors; the SDK having called the handler never makes it the executor. Not capturedHandler arguments and return values are never captured. If a field is surfaced it reads exactly “Not captured” (grey #8a94a0), distinct from “unknown” (amber) and from an empty value (“—”). VersionsImporter accepts 1.0 and 1.1; one recording has exactly one version; recordings in a file may differ. Handler fields exist only in 1.1. A 1.0 or 1.1 span without invocation.kind="handler" is a generic method block and is never retro-labelled as a handoff. The import screen shows the version per recording; the recording banner in the diagram appends “· schema 1.0” or “· schema 1.1”. AuthorityIDs and explicit parent/caller fields are authoritative. Layout never infers causality from adjacent timestamps or shared hostnames. Ordering within a recording uses sequence, then monotonic_ns; recordings keep separate clocks (§12).

8 · Participants

Code lanesTwo lifelines inside the Mobile-client band: App code (owner = integrator) and SDK (owner = sdk). They are participants, not destinations: no origin chip, never counted in “origins”, never a target of an HTTP arrow. Header line 1 is the owner label; line 2 (mono, 10.5 px) lists the components seen on that lane, e.g. “CustomerTaskHandler · SampleFlow”. Server lanesUnchanged: one lane per origin in order of first contact, discovered from HTTP events only. A handler with zero HTTP adds no lane. A handler's child HTTP to a new host adds that host as usual. Component expansionLane header “[+] components” splits a code lane into one sub-lane per component (max 4 visible, the rest grouped as “n more”), still inside the band with the owner label spanning them. Sub-lanes are 120 px, share the owner tint, and collapse back with “[−]”. Expansion is per owner and persists per session. Bars and local arrows move to the component sub-lane; HTTP arrows keep originating from the component sub-lane of their initiator. Two SDK componentsCollapsed: bars share the SDK lane and differ by the component line under the method label (“acceptTask · DemoAuthSdk” vs “flush · DemoAuthTelemetry”). Expanded: separate sub-lanes. Repeated callsSame component + method invoked n times: each block is labelled “loadTask() #k”; the span id appears only in the inspector (Attribution) and the accessible name, never on the canvas. Numbering is per recording, in sequence order. Nested callsA handler that calls back into the SDK produces an app → SDK call arrow and an SDK block at depth + 1 (3 px offset, as for nested operations). Depth follows parent_span_id only. Same-role callsSDK → SDK or app → app invocations (caller.owner = origin.owner) draw a self-call: a 12 px loop on the right side of the lane with the same open head, block at depth + 1. Never rendered as a cross-lane arrow. Uninstrumented callerIf parent_span_id is missing or does not resolve, the call arrow still starts on the lane of invocation.caller.owner, from a 6 px hollow dot instead of a bar, labelled “caller not instrumented”; the caller name comes from the label and is shown in the inspector. No SDK bar is invented.

9 · Invocation grammar and layout rules

Call arrowAt operation.started: solid 1.5 px #4f4a8a from the caller bar edge to the callee lane, open (stroke-only) arrowhead. Label mono 600: “call · loadTask()”; sub-label sans 10 px: “handler · synchronous”. HTTP arrows keep filled heads and #1b2430 — the two are distinguishable in greyscale. Handler block14 px bar on the callee lane, fill #ecebf6, stroke #4f4a8a 1.5 px, from the call row to the completion row. Label “loadTask() · handler”, sub “CustomerTaskHandler ← DemoAuthSdk.authenticate”. It is a method block: collapsible, listing “n requests hidden” when collapsed. Return / unwindAt operation.ended with matching span: dashed (4 3) 1.5 px arrow from the callee bar back to the caller's lane and bar (resolved by parent_span_id, else the caller label's owner lane), open head; colour and glyph per the §7 table. Duration label = duration_ns formatted, described in tooltips and the inspector as “elapsed, includes nested HTTP and waiting”. Never “CPU” or “exclusive”. Waiting segmentThe caller bar stays open for the whole handler. Its overlap with the handler block is overlaid with a 45° hatch in #4f4a8a at 45 % and an italic 9.5 px label “waiting for loadTask”. The hatch is scoped to that one bar; other SDK bars (e.g. concurrent telemetry) render normally so no “whole SDK paused” reading is possible. ResumptionWork after the return (acceptTask) is an ordinary nested SDK block below the return row; the caller bar continues until its own operation.ended, labelled at the bottom “authenticate → returned · success”. Child HTTPRequests with parent_span_id = handler span sit inside the block rows; arrows start on the App-code lane (initiator = integrator) and end on the server lane, with the full request/response/outcome grammar of §2. Owner filter “SDK” hides them; owner filter “App” shows them even while the SDK caller is hidden. HTTP outliving the handlerIf the handler's operation.ended precedes the request's completion, the return arrow is drawn at its observed row, the block ends there, and the request's response/outcome rows continue below on the App-code lane. The exchange carries the “returned before completion” flag (existing returnedEarly) and the inspector's Children list marks it “completed after return”. The causal link is the ID, so filtering or collapsing the handler still hides/shows the request with it. One selectionCall arrow, block, return arrow and the waiting hatch share one invocationId (= span_id). Clicking any of them selects the invocation; all four take the accent stroke, the caller bar takes the related-bar accent. Row kinds (layout)Add call (36 px, coincides with opstart of a handler span) and return (30 px, coincides with opend). Priority order within one timestamp: rec, opstart/call, req, res, end, return/opend. Output adds localArrows[] and waitSegments[]; bars[] gain kind: 'method' | 'handler'.

DefaultLocal calls are in the sequence by default; nothing is hidden on first open. Kind filterSegmented “All · HTTP only · Local calls only” next to the owner segmented. “Local calls only” keeps method blocks and call/return arrows and hides HTTP rows (server lanes stay, greyed, so the layout does not jump). Ancestry indicatorIn “HTTP only” mode every hidden invocation that contains visible HTTP collapses to a 4 px #4f4a8a rule on its lane spanning its rows, with a pill “↦ inside loadTask() · handler” at its top. Clicking the pill selects the invocation; clearing the filter restores it. Handlers with no HTTP collapse to the pill alone. CollapseHandler blocks obey the existing [−]/[+]; collapsed handler reads “n requests · m calls hidden”. “Collapse all methods” includes handlers. CountsToolbar shows “12 requests · 3 handler calls · 1 other call” as separate numbers; the navigator row shows “12 req · 3 ↦”. Origins count excludes code lanes. 14 · Scope — synchronous now, asynchronous proposed

Implemented in this design: dispatch="synchronous" method calls whose return is the caller's resumption. A return arrow means the callee's method exit was observed on the caller's stack.
Not equated with a synchronous return: a method that returns after enqueueing work, a coroutine suspension and later resumption, or a callback/Future completing later. Under draft 1.1 these all produce completion=returned at method exit and are drawn as such — the viewer must not draw a second “continuation” arrow or extend the block.
Proposed (not in 1.1, not designed here): async continuation rendering would require, at minimum: invocation.dispatch ∈ {"async_enqueue","coroutine"}; operation.suspended / operation.resumed events carrying the same span_id and a continuation_id; a completion="delivered" variant with the delivering thread/dispatcher; and explicit links[] from the completion event to the originating span. Visual candidates (segmented blocks, a dotted “awaiting” lifeline) are deferred until that telemetry exists.
